# empty-task-add-fix バグ修正 設計書

## Overview（概要）

ToDo リストアプリ（`bugfix_workflow/todo-app`）において、入力欄が空欄または空白文字のみの状態で「追加」ボタンを押すと、中身のないタスクがリストに追加されてしまうバグ（バグ #1）を修正する。

修正方針は最小限かつ限定的とする。フォーム送信時のハンドラで、入力文字列の前後の空白を除去（trim）した結果が空文字であれば `addTodo` を呼び出さず、タスクの追加・再描画を行わない。これに加えて本修正では以下の 2 点を扱う。

- **保存値の trim（正規化）**: 空でない入力を追加する際は、trim 済みのテキストをタスクとして保存する。従来案の「trim 前の元文字列を保存」は撤回し、trim 済み保存に変更する。これは意図した挙動変更であり、Preservation の扱いにその旨を反映する。
- **空入力時の視覚的フィードバック**: 空欄・空白のみで「追加」を押したときは、タスクを追加しないことに加えて、入力欄に一時的なハイライト／シェイクなどの軽微な視覚的フィードバックを表示する。CSS クラスの付与と一定時間後の除去で実現する。

完了切替・削除・残り件数表示・リロード時の復元といった既存動作には手を加えない。対象ファイルは `bugfix_workflow/todo-app`（`app.js`, `style.css`。必要に応じて `index.html`）。

## Glossary（用語集）

- **Bug_Condition (C)**: バグを引き起こす条件。入力欄の文字列を trim した結果が空文字である状態（空欄・空白のみ）。
- **Property (P)**: バグ条件を満たす入力に対する望ましい動作。タスクを追加せず、リストと残り件数を変化させず、入力欄に軽微な視覚的フィードバックを表示する。
- **Preservation（プリザベーション）**: 修正によって変更してはならない既存の挙動。完了切替、削除、残り件数表示、リロード復元、および空でない入力に対する「追加が成功すること」。ただし、空でない入力の**保存されるテキスト値**は trim 化により意図的に変更される（後述）。
- **保存値の trim 化（意図した変更）**: 空でない入力の保存 text を `trim(input.value)` に正規化する変更。`NOT C(X)` かつ前後に空白を含む入力についてのみ F と F' で保存値が異なる。Preservation の例外として明示的に扱う。
- **視覚的フィードバック**: バグ条件を満たす入力（空・空白のみ）で追加を試みたときに、入力欄へ一時的な CSS クラスを付与し、一定時間後に除去することで表示する軽微な演出（ハイライト／シェイク）。
- **submit ハンドラ**: `app.js` 内でフォームの `submit` イベントを処理する関数。入力値を取得し `addTodo` を呼び出す。今回の修正対象。
- **addTodo(text)**: `app.js` 内でタスクオブジェクトを生成し `todos` 配列へ追加して再描画する関数。保存する text を trim 済みとする。
- **input.value**: 入力欄（`#todo-input`）の生の文字列。バグ条件の判定対象となる入力。

## Bug Details（バグ詳細）

### Bug Condition（バグ条件）

このバグは、ユーザーが入力欄を空欄のまま、または半角・全角スペースやタブなど空白文字のみを入力した状態で「追加」ボタンを押した（フォームを submit した）ときに発生する。submit ハンドラは入力値を trim せずにそのまま `addTodo` へ渡すため、中身のないタスクが `todos` 配列に追加され、リストに表示されてしまう。

**Formal Specification（形式仕様）:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type TaskInput   // 入力欄の生の文字列（input.value）
  OUTPUT: boolean

  // 前後の空白を取り除いた結果が空文字なら、バグを引き起こす入力
  RETURN trim(input.text) = ""
END FUNCTION
```

### Examples（具体例）

- 入力欄が空文字（`""`）のまま「追加」→ 期待: 何も追加されず、入力欄に軽微なフィードバックが出る／実際（未修正）: 空のタスクが 1 件追加される。
- 入力欄が半角スペースのみ（`"   "`）で「追加」→ 期待: 何も追加されず、入力欄に軽微なフィードバックが出る／実際（未修正）: 空白のみのタスクが追加される。
- 入力欄がタブ・全角スペースのみ（`"\t　"`）で「追加」→ 期待: 何も追加されず、入力欄に軽微なフィードバックが出る／実際（未修正）: 空白のみのタスクが追加される。
- 入力欄に `"買い物"` を入力して「追加」→ 期待通り: `"買い物"` のタスクが追加される（バグ条件に該当しない正常系）。
- 入力欄に `"  買い物  "`（前後に空白）を入力して「追加」→ 期待: `"買い物"`（trim 済み）が保存される／実際（未修正）: `"  買い物  "` が空白付きのまま保存される。

## Expected Behavior（期待する挙動）

### Preservation Requirements（維持すべき挙動）

**Unchanged Behaviors（変更してはいけない挙動）:**
- 空でないテキストを入力して「追加」を押したときに、タスクが 1 件追加されること（追加が成功する動作そのもの）。
- チェックボックス操作による完了／未完了の切り替え。
- 「×」ボタンによる該当タスクのみの削除。
- 未完了タスクの残り件数表示。
- ブラウザリロード時の localStorage からの保存済みタスクの復元・表示。

**Intentional Change（意図した挙動変更 — Preservation の例外）:**
- 空でない入力の**保存される text 値**は、`trim(input.value)` に正規化される。前後に空白を含まない入力では保存値は従来と同一だが、前後に空白を含む入力（例: `"  買い物  "`）では保存値が `"買い物"` に変わる。これはバグ修正の一部として意図した変更であり、Preservation の完全一致からは除外する。

**Scope（対象範囲）:**
バグ条件（trim 後が空文字）に該当しない入力・操作は、上記の trim 化を除きこの修正の影響を受けてはならない。これには以下が含まれる。
- 空でないテキストによるタスク追加（追加が成功すること自体は不変。保存 text のみ正規化）。
- チェックボックスによる完了状態の切り替え。
- 削除ボタンによるタスク削除。
- リロードによる復元表示。

（バグ条件を満たす入力に対する期待される正しい動作は「Correctness Properties」の Property 1 で定義する。）

## Hypothesized Root Cause（推定原因）

バグ記述と対象コードの確認結果から、最も可能性の高い原因は以下のとおり。

1. **入力値の検証欠如（submit ハンドラ）**: `form` の `submit` ハンドラが `input.value` をそのまま `addTodo(text)` に渡しており、空・空白の検証（trim + 空判定）を行っていない。これが直接の原因と考えられる。

2. **追加処理側での前提**: `addTodo(text)` は渡された `text` を無条件に `todos` に push しており、中身の妥当性を検証していない。また保存する text も生の値をそのまま用いている。検証と正規化をどこに置くか（ハンドラ側で trim 済み値を渡す）の設計判断が必要。

3. **trim の未適用**: 入力文字列に対して trim を行っていないため、視覚的に空に見える空白のみの入力が有効値として扱われ、かつ前後に空白を含む有効入力の保存値にも空白が残っている。

4. **視覚的フィードバックの不在**: 空入力を弾いた際に、ユーザーに「なぜ追加されないか」を伝える手掛かり（ハイライト／シェイク等）が存在しない。CSS クラスの付与／除去の仕組みを追加する必要がある。

観測メモ（要検証）: 現在の `addTodo` には `saveTodos()` の呼び出しが見当たらない。追加時の永続化が別経路（次操作時の save）に依存している可能性があるため、探索的テストで追加直後の永続化挙動も観測し、修正が既存挙動を変えないことを確認する。今回の修正は「追加抑制」「保存値の trim 化」「空入力時の視覚的フィードバック」を対象とし、それ以外の永続化仕様は変更しない。

## Correctness Properties（正しさのプロパティ）

Property 1: Bug Condition - 空入力ではタスクを追加せず視覚的フィードバックを出す

_For any_ 入力欄の文字列を trim した結果が空文字である入力（isBugCondition が true を返す）に対して、修正後の追加処理は SHALL タスクを追加せず（`todos` の件数・リスト表示・残り件数のいずれも変化させず）、かつ入力欄に一時的なハイライト／シェイクなどの軽微な視覚的フィードバックを表示する。

**Validates: Requirements 2.1, 2.2, 2.3**

Property 2: Fix - 空でない入力は trim 済みテキストで保存される

_For any_ バグ条件を満たさない入力（isBugCondition が false を返す）に対して、修正後の追加処理は SHALL 前後の空白を除去した trim 済みテキスト（`trim(input.value)`）をタスクの text として保存する。

**Validates: Requirements 2.4**

Property 3: Preservation - 既存操作の挙動維持（保存値の正規化を除く）

_For any_ バグ条件を満たさない入力・操作（isBugCondition が false を返す。空でないテキストの追加成功、完了切替、削除、残り件数表示、リロード復元を含む）に対して、修正後のコードは SHALL 修正前のコードと同一の結果を生成する。ただし、空でない入力の保存 text 値は `trim(input.value)` に正規化される点のみ意図的に異なる（この 1 点を除き完全一致）。

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5**

## Fix Implementation（修正内容）

### Changes Required（必要な変更）

推定原因が正しいと仮定した場合の変更は以下のとおり。

**File**: `bugfix_workflow/todo-app/app.js`

**Function**: フォームの `submit` イベントハンドラ（必要に応じて `addTodo` 側にも検証を補強）

**Specific Changes（具体的な変更）:**
1. **submit ハンドラでの trim と空判定**: `input.value` を取得後 `trim()` する。trim 結果が空文字の場合は `addTodo` を呼ばず、視覚的フィードバックを表示して `return` で処理を打ち切る。この場合、入力欄の値やリスト・件数の状態は変化させない。

2. **trim 済み値の保存**: バグ条件に該当しない場合のみ、trim 済みテキストを `addTodo(trimmed)` に渡して追加する。これにより保存 text が正規化される（Property 2）。追加成功後の入力欄クリアなど既存の後処理は維持する。

3. **視覚的フィードバックの実装（app.js + style.css）**: 空入力時に入力欄（`#todo-input`）へ一時的な CSS クラス（例: `input-error`）を付与し、`setTimeout` で一定時間後（例: 300〜500ms）に除去する。連続実行時の二重付与を避けるため、付与前に一度クラスを外して再付与する等の配慮を行う。`style.css` に該当クラスのスタイル（`@keyframes` によるシェイク、または一時的な枠線/背景ハイライト）を追加する。`index.html` は既存の `#todo-input` を利用するため原則変更不要。

4. **多重防御（任意・推奨）**: `addTodo(text)` の先頭でも `trim(text) === ""` の場合は追加しないガードを設けることを検討する。これにより将来の呼び出し経路が増えても空タスク混入を防げる。主眼は submit ハンドラでの抑制であり、Preservation を崩さない範囲に留める。

5. **既存機能への非干渉**: `toggleTodo`、`deleteTodo`、`updateCounter`、`render`、`loadTodos`、`saveTodos` のロジックには変更を加えない（保存値の trim 化は submit ハンドラ／`addTodo` の入り口で完結させる）。

## Testing Strategy（テスト戦略）

### Validation Approach（検証アプローチ）

2 段階のアプローチを取る。まず未修正コード上でバグを再現する反例をあぶり出し、次に修正が正しく機能し（追加抑制・視覚的フィードバック・trim 済み保存）、かつ既存挙動を維持することを検証する。

### Exploratory Bug Condition Checking（探索的バグ条件チェック）

**Goal（目標）**: 修正前に、バグを実証する反例を surface する。推定原因を確認または反証する。反証された場合は再仮説を立てる。

**Test Plan（計画）**: 各種の空・空白入力に対してフォーム送信をシミュレートし、`todos` の件数とリスト DOM が変化しないこと・視覚的フィードバックが表示されることをアサートするテストを書く。加えて前後空白付きの有効入力で保存値を観測する。これらを未修正コードで実行して失敗を観測し、原因を理解する。

**Test Cases（テストケース）:**
1. **空文字追加テスト**: `input.value = ""` で submit → 件数が増えず、入力欄にフィードバッククラスが付与されることを期待（未修正コードでは失敗する）。
2. **半角スペースのみ追加テスト**: `input.value = "   "` で submit → 件数が増えず、フィードバックが出ることを期待（未修正コードでは失敗する）。
3. **タブ・全角スペースのみ追加テスト**: `input.value = "\t　"` で submit → 件数が増えず、フィードバックが出ることを期待（未修正コードでは失敗する）。
4. **前後空白付きテキストの保存値テスト**: `input.value = "  買い物  "` で submit → `"買い物"`（trim 済み）が保存されることを期待（未修正コードでは `"  買い物  "` が保存され失敗する）。

**Expected Counterexamples（想定される反例）:**
- 空・空白入力の submit 後に `todos` の件数が増え、空のリスト項目が描画される。視覚的フィードバックも出ない。
- 前後空白付き入力で、空白を含んだままの text が保存される。
- 想定原因: submit ハンドラでの空判定欠如、trim 未適用、フィードバック機構の不在。

### Fix Checking（修正チェック）

**Goal（目標）**: バグ条件を満たすすべての入力に対して追加抑制と視覚的フィードバックが行われ、バグ条件を満たさない入力では trim 済みテキストが保存されることを検証する。

**Pseudocode:**
```
// 空入力: 追加されず、視覚的フィードバックが出る
FOR ALL input WHERE isBugCondition(input) DO
  before := todos の件数
  fixedSubmit(input)
  after := todos の件数
  ASSERT after = before            // 追加されない
  ASSERT feedbackShown(#todo-input) // 軽微な視覚的フィードバックが表示される
END FOR

// 非空入力: trim 済みテキストが保存される
FOR ALL input WHERE NOT isBugCondition(input) DO
  fixedSubmit(input)
  saved := 追加されたタスクの text
  ASSERT saved = trim(input.value)  // 前後空白を除去した値が保存される
END FOR
```

### Preservation Checking（プリザベーションチェック）

**Goal（目標）**: バグ条件を満たさないすべての入力・操作に対して、保存値の trim 化を除き、修正後の処理が修正前と同一の結果を生成することを検証する。

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  // 保存 text は trim(input.value) に正規化される（意図的な変更）。
  // それ以外（追加成功・件数増加・並び替え・完了切替・削除・件数表示・永続化）は F と同一。
  expected := F(input) の結果の保存 text を trim(input.value) に置換したもの
  ASSERT fixedSubmit(input) = expected
END FOR
```

**Testing Approach（アプローチ）**: プリザベーションチェックには property-based testing を推奨する。理由は以下のとおり。
- 入力ドメイン全体にわたって多数のテストケースを自動生成できる。
- 手動のユニットテストでは見落としやすいエッジケースを捕捉できる。
- 非バグ入力すべてに対して、trim 化を除き挙動が不変であることの強い保証を与える。

**Test Plan（計画）**: まず未修正コードで通常入力・各操作の挙動を観測し、保存 text を trim 済みに置き換えた期待結果を基準に、その挙動を再現する property-based テストを書く。

**Test Cases（テストケース）:**
1. **通常追加のプリザベーション**: 空でないテキストの追加が成功する動作が修正後も不変であることを確認する（保存 text は trim 済みで比較）。
2. **完了切替のプリザベーション**: チェックボックス操作による完了／未完了切り替えが不変であることを確認する。
3. **削除のプリザベーション**: 「×」ボタンによる該当タスクのみの削除が不変であることを確認する。
4. **残り件数のプリザベーション**: 未完了タスク件数の表示が不変であることを確認する。
5. **リロード復元のプリザベーション**: localStorage からの復元・表示が不変であることを確認する。

### Unit Tests（ユニットテスト）

- 空文字・半角/全角スペース・タブのみ入力で追加されず、入力欄にフィードバッククラスが付与・一定時間後に除去されることのテスト。
- 前後に空白を含む有効テキスト（例: `"  買い物  "`）が trim 済み（`"買い物"`）で保存されることのテスト。
- 空でないテキスト追加・完了切替・削除が（保存値の trim 化を除き）従来どおり動作することのテスト。

### Property-Based Tests（プロパティベーステスト）

- ランダムな空白文字列（長さ・種類を変化）を生成し、いずれも追加されず視覚的フィードバックが表示されることを検証する。
- ランダムな非空文字列（前後にランダムな空白を付与）を生成し、保存 text が常に trim 済み値と一致することを検証する。
- ランダムな操作列（追加・切替・削除）を生成し、非バグ入力に対して保存値の trim 化を除き修正前後で結果が一致することを検証する。

### Integration Tests（統合テスト）

- 空入力で追加を試み、視覚的フィードバックを確認した後、有効入力で追加する一連のフローが正しく動作することを確認する。
- 前後空白付き入力の追加→保存→リロード復元で、trim 済みテキストが復元されることを確認する。
- 追加→完了切替→削除の一連の操作フローが不変であることを確認する。
