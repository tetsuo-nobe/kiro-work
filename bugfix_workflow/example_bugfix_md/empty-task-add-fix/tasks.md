# 実装計画（Implementation Plan）

- [x] 1. バグ条件の探索的再現テストを書く（修正前）
  - **Property 1: Bug Condition** - 空入力ではタスクを追加せず視覚的フィードバックを出す
  - **重要**: このテストは修正前のコードで必ず失敗する。失敗こそがバグの存在を証明する。
  - **禁止事項**: このテストが失敗しても、テストやコードをここで修正しないこと。
  - **備考**: このテストは期待挙動（空入力では件数・リスト・残り件数が変化せず、入力欄に視覚的フィードバックが表示される）を符号化しており、修正後にパスすることで Fix Checking の役割を果たす。
  - **目標（GOAL）**: バグを実証する反例を surface する（`todos` の件数が増える／空のリスト項目が描画される／フィードバックが出ない）。
  - **Scoped PBT アプローチ**: 空白文字の集合（半角スペース・タブ・全角スペース・改行など）からランダムに長さ・種類を変えた文字列を生成し、`trim` 後が空文字になる入力全体（`isBugCondition(X) = (trim(input.text) = "")` が true）へプロパティをスコープする。空文字 `""` も具体ケースとして含める。
  - `bugfix_workflow/todo-app/app.js` の submit ハンドラ経路（`input.value` 設定 → フォーム submit）をシミュレートし、以下をアサートする（design の Bug Condition / isBugCondition 由来）:
    - 送信前後で `todos` の件数と `#todo-list` の項目数が変化しないこと（追加されない）。
    - 送信後に `#todo-input` へ一時的な CSS クラス（例: `input-error`）が付与されること（`feedbackShown(input)`）。
  - **保存値観測**: 併せて `input.value = "  買い物  "`（前後空白付き・非バグ条件）で submit したとき、未修正コードで保存される `text` が生の `"  買い物  "` のままであることを観測・記録する（Property 2 の反例根拠）。
  - 未修正コードで実行する。
  - **想定される結果（EXPECTED OUTCOME）**: テストは失敗する（＝バグが存在することの証明として正しい）。空入力で件数が増え、フィードバッククラスも付与されないため。
  - 見つかった反例を記録し根本原因を理解する（例: 「`input.value = ""` で submit すると件数が 0→1 に増え、空の `<li>` が描画され、`input-error` クラスも付与されない」「`input.value = "   "` / `"\t　"` でも空白のみのタスクが追加される」「`"  買い物  "` が trim されず空白付きで保存される」）。
  - テストを書き、実行し、失敗を記録した時点でこのタスクを完了とする。
  - _Requirements: 1.1, 1.2, 2.1, 2.2, 2.3, 2.4_

- [x] 2. プリザベーションのプロパティテストを書く（修正前）
  - **Property 2: Preservation** - 既存操作の挙動維持（保存値の正規化を除く）
  - **重要**: observation-first（観測優先）方法論に従う。まず未修正コードを実行して実際の出力を観測し、その観測結果を再現するテストを書く。
  - 観測: `input.value = "買い物"`（前後空白なし・非バグ条件）で submit すると `todos` が 1 件増え、テキスト `"買い物"` の項目が描画される。
  - 観測: チェックボックス操作で該当タスクの `done` が切り替わり、`updateCounter` の残り件数表示が更新される。
  - 観測: 「×」ボタンで該当タスクのみが削除される。
  - 観測: `localStorage`（キー `bugfix-todo-app`）に保存されたタスクが `loadTodos` → `render` でリロード時に復元・表示される。
  - 上記の観測に基づき property-based テストを書く（design の Preservation Requirements 由来）:
    - 空でなく**前後に空白を含まない**ランダム文字列（`trim` 後が非空かつ `x === x.trim()`、`isBugCondition(X)` が false）を生成し、追加後に件数が 1 増え、描画テキストと保存 `text` が入力と一致することを検証する（trim 化の影響を受けない範囲で完全一致を確認）。
    - ランダムな操作列（追加・完了切替・削除）を生成し、非バグ入力に対して件数表示・並び順・永続化が観測どおりであることを検証する。
  - **注意**: 前後に空白を含む入力の保存 `text` は修正後に `trim` 済みへ正規化される（意図した変更）。この 1 点は Property 3 の対象外とし、本テストでは前後空白なし入力に限定して不変性を確認する。
  - 未修正コードで実行する。
  - **想定される結果（EXPECTED OUTCOME）**: テストはパスする（＝維持すべきベースライン挙動の確認）。
  - テストを書き、実行し、未修正コードでパスすることを確認した時点でこのタスクを完了とする。
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5_

- [x] 3. バグ #1（空欄でもタスクが追加できてしまう）の修正

  - [x] 3.1 submit ハンドラで空入力抑制・trim 済み保存・視覚的フィードバックを実装する
    - `bugfix_workflow/todo-app/app.js` のフォーム `submit` イベントハンドラを修正する。
    - `input.value` を取得後 `trim()` する。trim 結果が空文字の場合は `addTodo` を呼ばず、視覚的フィードバックを表示して `return` で処理を打ち切る（状態は一切変化させない）。
    - **視覚的フィードバック**: `#todo-input` へ一時的な CSS クラス（例: `input-error`）を付与し、`setTimeout` で一定時間後（例: 300〜500ms）に除去する。連続実行時の二重付与を避けるため、付与前に一度クラスを外して（再フロー後に）再付与する等の配慮を行う。
    - **trim 済み保存**: バグ条件に該当しない場合のみ、trim 済みテキストを `addTodo(trimmed)` に渡す。これにより保存 `text` が正規化される（Property 2）。追加成功後の入力欄クリアなど既存の後処理は維持する。
    - 多重防御（任意・推奨）として `addTodo(text)` 先頭に `trim(text) === ""` のガードを設けることを検討する。ただし Preservation を崩さない範囲に留める。
    - `bugfix_workflow/todo-app/style.css` に `input-error` クラスのスタイル（`@keyframes` によるシェイク、または一時的な枠線/背景ハイライト）を追加する。`index.html` は既存の `#todo-input` を利用するため原則変更不要。
    - `toggleTodo`・`deleteTodo`・`updateCounter`・`render`・`loadTodos`・`saveTodos` のロジックには変更を加えない。
    - _Bug_Condition: isBugCondition(input) = (trim(input.text) = "")（design より）_
    - _Expected_Behavior: バグ条件を満たす入力では追加せず件数・リスト・残り件数を変化させず視覚的フィードバックを表示（Property 1）。非バグ入力は trim 済みテキストを保存（Property 2）（design より）_
    - _Preservation: 空でない入力の追加成功・完了切替・削除・件数表示・リロード復元を維持（保存値の trim 化を除く。design Property 3 より）_
    - _Requirements: 2.1, 2.2, 2.3, 2.4, 3.1, 3.2, 3.3, 3.4, 3.5_
